## 一、那次警告是怎么来的

```
2026-10-12 15:59  账号异常提醒  —— 浏览行为与真人操作习惯不一致
2026-10-13 06:23  账号违规预警  —— 疑似使用三方工具或脚本自动浏览/查看/发布
```

**不是选择器写错了，是行为模式不像人。** 具体三处：

| 破绽 | 机制 | 我们当时做了什么 |
|---|---|---|
| **时序微结构** | 人的动作间隔高方差、重尾（2秒 → 40秒 → 5分钟）；脚本是紧凑的低方差流 | 固定 22 秒间隔，方差近零 |
| **会话宏结构** | 人深度优先：搜索 → 打开一篇 → 停留 → 看相关 → 游走。爬虫广度优先：搜 A、搜 B、搜 C…从不点进 | **关键词列表从头跑到尾** |
| **动作构成** | 真实会话混合点赞/收藏/停留/滚动/看视频；研究跑 100% 是读、零停留、零互动 | 打开页 → 取数据 → 关掉 |

还有两个叠加因素（已修）：

| | 问题 | 修法 |
|---|---|---|
| 无头浏览器 | 没有真实窗口和合成器行为 | 默认有头（`browser.py`）|
| JS 覆盖 webdriver | `defineProperty` 的 getter 不是原生的，读 `toString()` 就露馅 | 删掉，改用 `--disable-blink-features=AutomationControlled` |

## 二、核心认知：优势是耐心，不是速度

> 检测建模的是「人类会话长什么样」，标记不像的。
> **Agent 的真正优势不是快，是能跑 8 小时人形循环 —— 没人做得到。**
> 激进模仿了唯一会害你被抓的人类特质：急躁。

所以我们不追求"跑得快"，追求**"跑得久而像人"**。

## 三、读操作的节奏（Steady 是默认）

| 模式 | 每项节奏 | ~读/分 | 门槛 |
|---|---|---|---|
| **🚶 Steady（默认）** | **20s ± 50% jitter**（≈10-30s） | 2-3 | 无 |
| 🐢 Deep | 60-120s | 0.5-1 | 大任务 opt-in |
| ⚡ Fast | ≥5s | 10+ | **需打印警告 + 用户确认**，仅限当次 |

**所有模式的不变量：**

1. **一篇在途**，绝不并行
2. **<5 读/分**，除 Fast 外绝不持续越线
3. **每次等待加 ±50% 随机 jitter** —— 匀速是机器签名
4. **绝不零延迟**

## 四、硬规则（不可协商）

| # | 规则 | 为什么 |
|---|---|---|
| 1 | **循环强制**，>5 项的采集必须走循环 | 一次性批量跑是签名 |
| 2 | **一篇在途**，不并行不批量 | 并发是机器特征 |
| 3 | **始终 jitter** | 匀速间隔方差近零 |
| 4 | **评论分页 ≤3 页**，不深爬 | 评论是最先触发风控的端点 |
| 5 | **每项 checkpoint 落盘** | 会话被杀可恢复 |
| 6 | **每日预算 ≤200 详情读** | 异常量本身就是触发器 |
| 7 | **熔断器绝对** —— 见到第一个风控信号立即 STOP，**绝不自动重试** | 重试会把软节流升级成数小时封禁 |
| 8 | **读非写** —— 研究工作流不掺互动动作 | 动作构成异常 |

### 熔断触发条件（任一即停）

```
NeedVerify / 验证码
空响应 {}          ← 多半是 token 过期，重新播种，别盲重试
Session expired    ← cookie 失效，重新登录
IP 封 300012       ← 硬限速，等或换网
```

触发后：持久化状态、标记 `breaker: tripped`、当前项留 `pending`、**告知用户**。
只有人工显式确认才能恢复。

## 五、搜索类采集的正确形态

### 零风险那一档：读别人的聚合站

**不产生任何小红书账号的行为痕迹，所以不受平台风控约束。**
这是唯一能长期高频跑的一档，也是热点的主要来源。

已接进 `工作台/hotlist.py`：

```powershell
python hotlist.py          # 拉热搜 + 筛相关 + 看本月季节节点
python hotlist.py --all    # 看原始热搜
```

| 源 | 形态 | 备注 |
|---|---|---|
| `https://remoshuang.com/` | 静态 CDN 文件 | `daily/<日期>.md`（人工审核 TOP 30）、`hot/<日期>.md`（实时快照）、`feed/tech.xml`、`feed/rising.xml` |
| `v2.xxapi.cn` / `60s.viki.moe` | 公益 JSON API | 微博/抖音/知乎/B站/百度/头条，随时会挂，留着兜底 |
| `tophub.today` / `top.open2hub.com` | 网页热榜 | 无官方 API，只能人工看 |

三个坑（实测踩过）：

1. **当天的 daily 要等北京时间 10:00 才发布**（统计周期 05:00→次日 05:00）
   → **必须日期回退**，否则早报天天拉不到
2. **会间歇 404** → 每个 feed 都要有 fallback
3. **`.isoformat()` 会带时间戳** —— `datetime.today().isoformat()` 出来是
   `2026-10-13T10:37:01`，拼进 URL 全 404。**必须先 `.date()`。**

⚠️ **这些源里没有一个是小红书**，`test_hotlist.py` 有一条断言专门守这个 ——
哪天有人手滑加了个小红书源，测试立刻红。

> ⚠️ **认清价值边界。** 全国热搜里和宽带相关的强相关条目**经常是 0**。
> 娱乐八卦占绝大多数，这不是故障，是常态。
>
> **真正有用的是季节节点**（开学 / 搬家 / 毕业 / 年末续费），
> 那是每年必来的大盘节奏，比蹭随机热搜靠谱得多。
> `hotlist.py` 已经把当月的季节选题一起打出来了。

### 必须碰平台时的形态

**广度枚举是签名。** 「搜 A、搜 B、搜 C…」这条路一眼就是脚本。

改法：

| ❌ 别做 | ✅ 改成 |
|---|---|
| 一次会话跑 4 个关键词 | **一次会话最多 1-2 个**，其余顺延到下次 |
| 关键词之间隔 22 秒 | **隔 5-15 分钟**（同一会话），或直接跨会话 |
| 搜完立刻关页面 | **停留**（读几条标题、滚动）|
| 纯读、零互动 | 偶尔点进一篇看看（深度）|
| 每次都是同样数量 | 数量本身也要随机 |

**如果只要关键词热度，用第三方聚合 API，完全不碰平台。**

Easel 的做法（`hotlist-apis.md`）：

```python
TREND_SOURCES = {
    "weibo":   ("https://v2.xxapi.cn/api/weibohot",  "https://60s.viki.moe/v2/weibo"),
    "douyin":  ("https://v2.xxapi.cn/api/douyinhot", "https://60s.viki.moe/v2/douyin"),
    "zhihu":   ("https://api.zhihu.com/topstory/hot-list?limit=50", ...),
    "bilibili":(...),
    "baidu":   (...),
    "toutiao": (...),
}
```

> 🚫 **禁止直接抓平台官网**（weibo.com / zhihu.com / douyin.com）——
> 它们对服务器 IP 有反爬，返回 403/验证码/空内容，不是数据。
> 建议 ≤1 次/分钟，平台侧缓存 300 秒。

**代价**：拿不到小红书站内的具体笔记数据。
**收益**：零账号风险。

**取舍**：站内数据必须爬的话，按第三、四节的节奏来，而且**低频**。

## 六、写操作的安全阈值

> ⚠️ **写操作现在全部由人工完成**（见 README「审核 → 导出 → 人工发布」）。
> 这张表保留两个用途：人工操作时同样别超过这些量；
> 万一将来要恢复某个自动化动作，这里是上限依据。

| 动作 | 安全间隔 | 单次上限 |
|---|---|---|
| 发帖 | 3-4 小时（2-3 帖/天） | — |
| 评论 / 回复 | ≥3 分钟 | 10 条/批 |
| 批量回复 | ≥3 分钟，5 分 ±30% jitter | 30 条硬上限 |

**触发风控的行为**：匀速时序、>50 互动/分、活动比率异常（评论多于浏览）、
设备指纹不匹配。

### 被限流后怎么恢复

**停止一切自动化，先手动养号 3-7 天。**

限流期间做任何自动化动作都会延长处罚周期 —— 这也是 `brake.py` 存在的理由。
手动养号 = 真人刷首页、看几条、偶尔点个赞，**不做任何运营动作**。

> 这条来自外部同类项目的风控规则（`leeguooooo/xhs-skill`），
> 和我们自己的判断一致，所以采纳。属于**未在本账号验证**的经验，
> 记进 `数据/待验证.md`。

## 八、自查

上线前对着过一遍：

```
[ ] 这次操作是读还是写？读写有没有混在一起？
[ ] 间隔是随机的还是固定的？方差够大吗？
[ ] 一次会话里跑了几项？超过 5 项走循环了吗？
[ ] 有没有并行？
[ ] 停留了吗？还是打开就抓、抓完就关？
[ ] 今天的读预算用完了吗？
[ ] 熔断器接上了吗？见到验证码会不会自动重试？
[ ] 这次跑的关键词数量，和上次一样吗？（一样也是特征）
```
